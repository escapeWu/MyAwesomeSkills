# 项目 Docs 工作流

这是一个薄编排层：帮助 Agent 找到必要上下文，并在任务完成后维护长期文档。它不取代代码分析、
项目测试或用户授权，也不要求每个任务产生文档。

## 快速原则

- 先做事，再整理长期文档。
- 开工前只读，不写 docs。
- 默认读取 1-3 份任务相关文档；缺少文档不自动阻塞实现。
- 不要求 TDD、测试先行、Spec、固定状态机、验证矩阵或阶段性 changelog。
- 只有目标或硬边界无法判断时才问用户；可逆细节沿用仓库惯例。
- 完成实现和验证后，主 Agent 发起一个异步 docs 子任务，集中做一次影响判断和一次增量更新。
- docs SubAgent 是该轮唯一文档 writer；主 Agent 不等待，也不再并发修改同一批 docs。

## 何时使用

适合：

- 非 trivial 功能、bug 修复、重构、API 或跨模块修改；
- 用户询问当前路线、进度、下一步或已实现行为；
- 文档与代码可能不一致，需要判断长期知识是否应更新；
- 外部建议已经被内部接受，准备在当前仓库中实施。

通常跳过：

- typo、格式调整、明确的单文件小修；
- 纯搜索或临时分析；
- 用户明确要求不改 docs；
- 本次变化不产生长期可复用知识。

## 工作流

### 1. 读取最小上下文

先读适用的 `AGENTS.md` / `CLAUDE.md`，然后按项目现有结构选择：

1. `docs/OVERVIEW.md`，如果存在且能帮助定位；
2. owning Feature 的 `README.md` / `INDEX.md`；
3. 一份直接相关的 reference、接口或运行文档；
4. 当前代码入口和相关测试。

不要为了遵循固定清单而创建缺失文件，也不要全量读取 `docs/`。文档是导航和历史上下文；当前代码
决定已实现行为，用户明确要求决定本次目标。

### 2. 只澄清真正阻塞的问题

当下列核心内容无法从请求、代码或现有文档判断时，才询问用户：

- 用户真正想要的结果；
- 会改变产品边界的 scope 选择；
- 安全、授权、数据损失、兼容性或不可逆迁移边界。

一次只问当前最关键的问题，并给出推荐默认值。不要询问可以在实现中安全决定的文件布局、函数名、
测试粒度、文档字段或其他可逆细节。

项目已安装 `add-idea` 时，未成形 idea 可以使用它；partial install 没有该 skill 时，直接按本节只澄清一个核心 blocker。两种情况都不要求先产出多份合同文档。

### 3. 实施与验证

- 在当前仓库模式内实现，不制造新的流程层。
- 保留用户已有修改，不顺手重构无关内容。
- 使用与风险和影响范围匹配的测试、lint、类型检查或手工验证。
- harness 不规定测试先行；优先复用项目已有验证方式。
- 复杂调用链或架构不清时，才升级到 `project-analysis`。

### 4. 任务完成后异步委派一次 docs pass

只有实现和必要验证完成后，主 Agent 才创建一个异步 docs 子任务。传给 SubAgent 的上下文应当小而完整：

- 用户目标与最终实现摘要；
- 实际修改文件和重要行为变化；
- 已运行的验证及结果；
- 候选 owning README/reference 路径；
- 只更新长期稳定事实、只做一轮增量 patch 的边界。

SubAgent 先集中检查下列长期影响：

| 变化 | 优先更新位置 |
|---|---|
| Feature 目标、边界、当前行为、重要限制或当前状态 | owning `docs/feature/<feature>/README.md` |
| 稳定跨模块接口、架构或运行方式 | 相关 `docs/reference/*.md` |
| 新增、删除或重命名模块，导致导航变化 | `docs/feature/INDEX.md` 和必要时 `docs/OVERVIEW.md` |
| 外部来源与内部采纳状态 | 对应 `docs/collaboration/<case>/INDEX.md` |

更新规则：

- 一个 SubAgent 负责全部必要写回，避免多个 writer 修改同一文档。
- 异步运行，不要求主 Agent 等待；文档是用户明确主交付物或会影响正确性时除外。
- 用一轮增量 patch 完成所有必要写回；不要边实现边反复改 docs。
- 只写完成后的稳定事实、长期约束和仍然有效的下一步。
- 不保存会话计划、中间分析、原始命令输出、逐文件进度或临时 checklist。
- 没有长期影响时不改 docs。
- 只有导航变化时才更新上层 INDEX/OVERVIEW，避免层层同步同一状态。
- 项目已有 ADR、changelog 或其他约定时继续沿用，但 harness 不主动要求新增这些体系。
- SubAgent 发现目标、产品边界或安全授权仍不确定时，不扩大文档；返回 blocker 或保持无修改。
- 环境没有 SubAgent 时，主 Agent 才在结束阶段执行同样的一次轻量 patch。

## 路线与进度

用户询问路线或进度时，直接使用语义化名称回答：目标、当前重点、阻塞和下一步。只有跨会话路线确实
变化且项目需要持久化时，才在 owning README 更新一行简洁路线或状态。不要为路线创建 node ID、DAG
manifest、阶段状态机或独立进度控制面。

若路线依赖关系复杂到无法可靠判断，使用 `project-analysis` 的 route-impact 分析；分析结论仍在任务
结束时统一写回。

## 向用户汇报

保持简洁：

- 完成了什么；
- 做了哪些验证；
- 已启动的异步 docs 维护范围，或为什么无需维护；
- 仍存在的 blocker 或风险。

不要默认展示内部阶段编号、文档维护清单或完整执行日志。
